Which Web Pages Should a Content Team Review First?

Sehrish Ejaz · FlyRank ML Internship · August 2026 · GitHub Repo

Abstract: Content teams managing large websites cannot review every page each week — the question is which pages to prioritize. Using a 30,000-row anonymized search dataset from FlyRank, this work trains a Random Forest classifier on staleness, impressions, and CTR signals to rank pages by observed decline likelihood. On a client-grouped test split, the model achieves Precision@50 of 0.720 versus a rule-baseline of 0.500 and a random base rate of 0.531. The output is a ranked content action queue — decision-support for a human editor, not an automated verdict.

1. Problem

A content editor managing hundreds of pages cannot review everything. Without a prioritization signal, teams either review randomly or rely on gut feeling — both waste editor time and miss real problems. This work asks: which pages show the strongest observed decline signals, and how can we rank them reliably?

The output supports one decision: where an editor spends their time this week.

2. Data

Source: FlyRank ML Internship dataset 30,000 rows 32 pseudonymized clients 90-day snapshot

The starter dataset contains one row per content page with trailing-90-day search and engagement signals. No client names, URLs, or raw queries appear in this work. The following were excluded:

  • avg_position = 0 — means no data, not rank zero
  • trend_direction and trend_pct — label-derived, excluded to prevent leakage
  • Pages with fewer than 200 impressions — too little traffic to justify editor time

3. Methodology

Label: is_declining_label = 1 when trend_direction == "down". This is a proxy label from the same 90-day snapshot — not a directly observed future outcome.

Features (7): days_since_last_update, impressions_90d, ctr, avg_position, content_age_days, word_count, has_wordcount (missingness flag).

Baseline (Week 4): Hand-written rule — stale × visible × (1 + low_ctr) × impressions. Reason codes: STALE_LOW_CTR, STALE_VISIBLE, NOT_STALE.

Models: Logistic Regression (readable, probability scores), then Random Forest (captures signal combinations, permutation importance verified).

Validation: Client-grouped split — 80% clients train, 20% clients test. No page from a test client appears in training. This tests generalization to unseen clients, not memorization.

Leakage checks: trend_direction and trend_pct confirmed excluded. Deliberately adding trend_pct inflated the score — confirming it is label-derived and correctly excluded from the clean model.

5. Limitations

  • No causation: refreshing a page will not guaranteed increase traffic. This is a cross-sectional snapshot — no intervention was measured.
  • Proxy label: is_declining_label is derived from trend_direction in the same window — not a future traffic measurement.
  • Generalization: 32 clients, one 90-day window. Performance on new clients or different time periods may differ.
  • SERP effects: low CTR may reflect SERP layout changes, not content quality — a refresh may not help.
  • Algorithm changes: a major Google update can shift all signals; retrain after any such event.

6. Ranked Recommendations

PriorityReason CodeActionWhy
1STALE_LOW_CTRrefresh Old + low CTR — strongest observed decline signal
2HIGH_POSITIONrefresh Ranking below position 20 + stale — relevance likely issue
3STALE_VISIBLEmonitor Good impressions but stale — watch before acting
4LOW_TRAFFICskip Too few impressions to justify editor time
5NOT_STALEskip Recently updated — leave it alone

Human review required before any action:

  • Confirm page is not under an active campaign
  • Check CMS for recent edits not yet indexed
  • Verify content is still strategically relevant

Never automate:

  • Publishing content changes from score alone
  • Deleting or redirecting pages without human sign-off
  • Applying the queue to legal or compliance content
